Which pages should a content team refresh first?

Zeina Farghaly · FlyRank ML Internship Capstone (ML-11) · github.com/zeinafarghaly-arch/ML-flyrank · August 2026
Abstract

FlyRank content teams may have many pages to review, but limited time to decide which pages deserve attention first. This paper asks whether a simple machine-learning model can use observed search and engagement signals to rank pages that may need a content refresh, and whether it can improve on a simple rule-based approach. Using an anonymized sample of 30,000 content pages from 32 pseudonymized clients over a rolling 90-day window, I trained a Logistic Regression model using six non-leaking features. I evaluated it on a client-grouped holdout set using Precision@500. The model scored 0.528, compared with 0.490 for the rule-based baseline and 0.517 for the test-set base rate. The improvement is small, but it suggests that a ranked shortlist can provide useful decision support for human content review. It should not be treated as an automatic system for deciding which pages must be refreshed.

01

Introduction

A content team handling many clients' sites can't open every page each month to check how it's doing. Someone has to pick which pages get looked at first, since a reviewer's time is limited. Right now that choice is often made with a simple rule — "check anything old" — which treats every old page as equally urgent, even if it still gets plenty of traffic.

This paper looks at a smaller, more answerable version of that problem: using what we can already observe about a page's search and engagement history, can a model rank it by refresh urgency better than a simple rule can? Each row studied is one content page. The output is a ranked shortlist, with a plain-language reason next to each pick. A human then takes action from that list — refresh, expand, or leave the page alone. Getting it wrong costs a reviewer's time on a page that didn't need it, or lets a page quietly keep losing traffic.

What a row is, and the label

Each row is one content page, with search and engagement numbers added up over a rolling 90-day period ending when the data was exported. The label comes straight from the dataset's own trend_direction field: is_declining = (trend_direction == "down") — 16,262 of 30,000 pages (54.2%) have that label.

What was left out, and why

  • trend_direction, trend_pct — the label comes straight from these, so using them as inputs would basically hand the model the answer (proven in section 3).
  • impressions_last_30d, impressions_prev_30d — these are the two time windows the trend label is calculated from, close enough that they'd leak the answer too.
  • content_id, client_id — hidden ID numbers, used only to keep each client's pages together during the train/test split, never fed into the model.
  • Client names, website addresses, page titles, and real search terms — none of these are in this file; they were removed before it was shared with interns.
A note on privacy. Everything in this paper comes from the anonymized starter file above. No detail that could identify a client, no website address, and no real search term appears anywhere in this project or on this page.
03

Methodology

The baseline rule

A simple, easy-to-check rule from Week 4: 0.6 × staleness + 0.4 × search demand, with both parts scaled to fit the dataset. It sets a fair starting point without any training.

The model

A logistic regression model using six inputs — days_since_last_update, search_volume, avg_position, ctr, engagement_rate, content_age_days — with class_weight="balanced" and random_state=42. This type of model was chosen because the label is a real, observed yes/no answer (not a made-up ranking), and it gives a probability score that's easy to explain to someone without a technical background.

How it was tested

Pages are split by client_id, not by row (GroupShuffleSplit, 25% for testing, seed 42) — so no client shows up on both sides of the split, and the model is tested only on clients it has never seen before. This matters a lot: if you split rows at random instead, almost every client ends up leaking into both sides.

Simple random split
31 / 32

clients show up in both the training set and the test set — so the model can partly just recognize patterns from specific clients instead of learning general ones.

Client-grouped split
0 / 32

clients overlap. Every client in the test set is one the model has never seen while training — a fair test of whether it truly learned something general.

Checking for leaks

To make sure the excluded features really did matter, I added each one back on its own and watched what happened to Precision@500:

Added featurePrecision@500Jump vs. honest model
impressions_last_30d0.548+0.020
impressions_prev_30d0.528+0.000
trend_pct1.000+0.472

Adding trend_pct pushes Precision@500 up to a near-perfect 1.000 — clear proof that it (and trend_direction along with it) is where the label actually comes from, not a fair feature to predict with. The two impression-window features barely move the score, which fits with them carrying related but not identical information. This check is why 0.528 is the number reported here, instead of an inflated, leaked one.

Results

The model, the baseline rule, and a random guess, all scored on the exact same set-aside test rows, grouped by client:

MethodPrecision@500
Base rate (random guess)0.517
Baseline rule (Week 4)0.490
Logistic regression (this capstone)0.528

What the model relies on most

Ranked by how much weight each one carries: content_age_days (−0.396), days_since_last_update (+0.237), and ctr (−0.202) matter the most; engagement_rate, search_volume, and avg_position barely matter. In this data, older, staler pages with fewer clicks were most likely to be marked "declining" — which fits the idea that staleness and weak clicks drive decline, though it doesn't prove it.

Where it gets things wrong

Looking at the model's most confident wrong guesses in the top 500: several are pages with no measured search volume and 183 days since their last update — they look as stale as possible by every measure the model has, yet they weren't actually declining. Staleness alone isn't a perfect signal; some old pages simply don't need an update. That's a fair limit of a model with only 6 features, not a flaw.

05

Limitations & honest framing

  • A weak signal, not a strong one. Precision@500 (0.528) is close to the random-guess rate (0.517). The fair improvement over the rule-based baseline is about 4 points — real, but small.
  • One snapshot, one dataset. Trained and tested on a single 30,000-row, 32-client starter file covering one rolling 90-day period — it hasn't yet been checked against the full ~79M-row database or against new clients.
  • The label is a stand-in, not a real outcome. is_declining compares two time windows at a single moment. Nothing here has been tested against what actually happened after a page was reviewed or refreshed.
  • It can't prove cause and effect. The model can say a page looks like pages that declined before. It can't say that refreshing a page will fix it — proving that would need an experiment this dataset doesn't support.
  • Only six number-based features. The model knows nothing about content quality, brand voice, the time of year, or business priorities — a human reviewer still needs to weigh all of that before acting.
Careful-language check: every result on this page is described as something observed or measured, not as a certainty — meant to support a human reviewer's decision, never to replace it.
06

Ranked recommendations

Scoring only the 8 test clients the model never saw during training — since that's the only group with a proven precision number — sorts 7,115 pages into five actions, each with a plain-language reason so a reviewer can double-check the pick in seconds:

  1. 1

    Refresh and review CTR — 1,922 pages

    Ranks well, but gets surprisingly few clicks. Quickest win: the page already ranks, so fixing the title or snippet might boost clicks without rewriting the content.

  2. 2

    Refresh — 439 pages

    Hasn't been updated in 90+ days, but still gets real traffic. Worth an editor's pass before it fades further.

  3. 3

    Expand and refresh — 344 pages

    Short content (under 2,000 words) that real people are searching for — a good candidate for adding more depth, not just a quick touch-up.

  4. 4

    Human data check — 64 pages

    No ranking-position data at all. This is a gap in tracking, not proof the page is fine — check the tracking setup before trusting any score for these pages.

  5. 5

    Monitor — 4,346 pages

    Everything else. No action needed this cycle.

Before acting on any page

A human reviewer should still check three things: does the reason actually make sense for that page, is there some outside cause the model can't see (a paused ad campaign, the season, a site problem), and is the page still important enough to the business to spend review time on.
